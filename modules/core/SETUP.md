# Setting up meetings

This is the authoritative setup reference for the meetings module. An agent helping a person set up
their workspace reads it from the installed package root (for example
`node_modules/@dreamteamer/core/SETUP.md`) and follows it in the person's own language.

Meeting records, screenshots and contact stamps work with **no setup at all**. Everything below is
for the optional calendar sync (`/fetch-meetings`); the person may skip it.

## Scope

One setup unit, `meetings`. Owns: `WORK_CALENDARS` (which calendars count as work, their default
company and the account that reads each), and the local prerequisites of the calendar reader
`gcal.mjs`. Does not own: Google consent or the credential directory (the `google-workspace` module's
SETUP.md, when installed), transcription (the `recordings` module), or `FILES_FOLDER`/`INBOX_FOLDERS`.

## Commands

Run from the workspace root. The engine drives the unit the same way however the module arrived — its
own package or an inline copy. (Through core 0.11 it could also arrive composed into `@dreamteamer/core`;
from core 0.12.0 core is a preset of the small modules, so this does not apply.)

| command | effect |
|---|---|
| `dt status` | The unit's line: `configured`, `blocked` or `ready`, with the next command. Read-only. |
| `dt doctor` | The unit's checks as rows. Read-only, offline. |
| `dt setup meetings --input calendar="<calendar> \| <company> \| <account>"` | Merges the rows into `WORK_CALENDARS` in `.env` (repeat `--input` per row). `--json` lists what is pending. |
| `dt setup meetings --verify --authorize` | The owner's live check, in a terminal. |

## Inputs to ask for

One row per work calendar: the calendar id, the default `companies` id (or `mixed` for a calendar
holding several companies' meetings) and the account email that reads it. See the
`fetching-meetings` skill for which calendars count as work.

## Reading a check

| status | meaning | what to say |
|---|---|---|
| `configured` | The value or file exists. **Not** proof the account can read the calendar. | configured, unverified |
| `unverified` | Only the live step can establish it. Never inferred from `ok`. | unverified |
| `missing` | An input or action can fix it. | needs input or action |
| `blocked` | Waits on another row, or a fix by hand is needed — the reason says which. | blocked, with the reason |

`meetings.account-access` is `unverified` until a live check passes. Check rows carry counts and line
numbers, never a calendar id, account address or path.

## Actions

1. **`add-calendar-rows`** — an env action: the unit merges the rows into the `WORK_CALENDARS` value
   (rows already present are kept; nothing new is `done`), and the engine writes `.env` — that key
   only, every other line byte for byte, the value never printed. A mixed batch adds the valid rows
   and names the malformed ones by input number.

   **It changes nothing, and says why, when:** `.env` could be committed, holds the key twice or has a
   temporary file from an interrupted write beside it (the engine's refusals); `WORK_CALENDARS` is set
   in the process environment, which would shadow `.env`; an existing row is malformed; or a requested
   row names an existing calendar and account with a different company — edit that by hand.
2. **Account consent** — the owner's step, owned elsewhere. With `@dreamteamer/google-workspace`
   installed, follow its SETUP.md (`authorize-account`). Otherwise follow the one-time setup in the
   `fetching-meetings` skill. This module never starts consent.
3. **`verify-calendar-access`** — the owner's, live, under `dt setup meetings --verify --authorize`.
   Effects: network (token refresh at Google and one calendar-list read per account). Evidence: every
   row reports `verdict: full`, and a dated receipt makes the line `ready · verified`. The output names
   private calendars: report only how many rows are `full`, `free-busy` or `absent`.

The calendar reader reads `GOOGLE_CLIENT_SECRET_PATH` and `WORKSPACE_MCP_CREDENTIALS_DIR` from the
**process environment** (defaults under `~/.config`), and `WORK_CALENDARS` from the environment or
`.env`. Inspect looks exactly where the reader will.

## Final report

**ready** only after `verify-calendar-access` showed every row `full`; **configured, unverified** when
rows and credential files exist without a live check; **blocked** with the blocking row; **skipped**
when the person declined calendar sync (`dt setup meetings --skip`). Name the next action for each.

## Limits

- File presence proves nothing about consent, expiry, scopes or calendar access.
- Through core 0.11, `@dreamteamer/core` composed this reference into its own root `SETUP.md`; from core
  0.12.0 core is a preset of the small modules and this file is the only copy.

# Setting up recordings

Recording records, inbox ingestion and matching work with no setup. Offline transcription needs this
machine prepared, and the module declares that as its **setup unit** (`dt status` lists it as
`recordings`); the engine drives it — nothing here is a command to type by hand except these:

```bash
dt install @dreamteamer/core --input files_folder=<folder> --allow download --allow machine
dt setup recordings --verify --allow machine        # one CPU transcription of the shipped clip
```

- **Inputs:** `files_folder` (FILES_FOLDER, required — where recordings are archived), `inbox_folders`
  (INBOX_FOLDERS, optional), `transcription_home` (TRANSCRIPTION_HOME, default
  `~/.cache/dreamteamer/transcription` — the models and the venv, outside the workspace and outside
  `node_modules`, so neither compile nor npm touches them).
- **Checks:** `ffmpeg` and `uv` on PATH (blocked until they are — `brew install ffmpeg uv`); the three
  keys in `.env`; the venv; the CPU pass's three model files; the CPU run's receipt.
- **Actions and their effects:** `set-home` writes the keys into `.env` (workspace-files);
  `provision-venv` runs `uv sync` (machine); `download-models` fetches ~1.6 GB (download);
  `verify-cpu` transcribes `lib/clip.wav` — generated speech, nobody's voice — on the CPU and keeps a
  dated receipt (machine). The GPU pass is not set up here.
- **Reading `dt status`:** `configured` with "CPU run unverified" means the models are on disk and
  never ran; `ready · verified <date>` means they did, on this computer, that day.

Every command runs through `bin/transcribe.mjs`, which reads `.env` and sets `UV_PROJECT_ENVIRONMENT`
before spawning uv; the skill's commands go through the same entry.

# Setting up files

One setup unit (`dt status` lists it as `files`): the input `files_folder` (FILES_FOLDER, required) — the mounted root every `file-drives` record resolves under — written into `.env` by `set-files_folder` (a workspace-files effect). The check reads `configured` when the key is set and the folder exists, `blocked` when it is set but not there (a drive not mounted), `missing` when unset. Nothing downloads, nothing reaches the network; `dt files sync` is the next command once a drive record exists.
